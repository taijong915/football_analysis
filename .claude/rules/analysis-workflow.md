# 분석 워크플로우 상세 가이드

`CLAUDE.md`의 "분석 워크플로우" 요약을 풀어쓴 상세 규칙입니다. 새 분석 주제를 논의하거나, 주제 폴더를 만들거나, 재사용 함수를 개발할 때 참고하세요.

이 프로젝트에서 새 분석 주제는 항상 다음 4단계를 거칩니다: **아이디어 논의(`ideas/backlog.md`) → 데이터 검토 → 분석 주제 폴더 및 파일 구성 → 해당 폴더 안에서 산출물 관리**.

## 1단계 - 아이디어 논의 (`ideas/backlog.md`)

`ideas/`(분석 주제 브레인스토밍)와 관련된 대화에서는 답을 바로 나열하는 대신 **질문증강(question augmentation) 방식**으로 소통하세요. 즉, 사용자가 던진 주제나 관심사를 곧장 완성된 아이디어 목록으로 바꾸지 말고, 되묻는 질문을 통해 사용자 스스로 생각을 구체화하도록 돕는 역할을 합니다.

- 사용자가 막연한 관심사(예: "메시 관련해서 뭔가 해보고 싶어")를 던지면, 바로 아이디어를 제안하기보다 관점을 넓히거나 좁히는 질문을 먼저 던지세요 - 어떤 대회/시즌에 관심 있는지, 개인 기록 중심인지 팀 전술 맥락인지, 이미 본 적 없는 새로운 인사이트를 원하는지 등.
- 여러 질문을 한 번에 쏟아내지 말고, 답변에 따라 다음 질문을 이어가며 대화로 좁혀가세요.
- 사용자가 충분히 구체화됐다고 판단되면 정리한 내용을 `ideas/backlog.md`의 형식(분석 질문/필요 데이터/예상 산출물)으로 요약해 제안하고, 사용자 확인 후 `구체화` 상태로 기록하세요.
- 사용자가 명시적으로 "그냥 아이디어를 던져줘/브레인스토밍해줘"라고 요청하면 질문 없이 바로 아이디어 목록을 제시해도 됩니다 - 이 방식은 기본값이지 강제 규칙이 아닙니다.

## 2단계 - 데이터 검토

`PLAN.md`의 방법론을 확정하기 전에, 그 방법론이 의존하는 데이터 필드가 실제 대상 경기/대회에서 얼마나 신뢰할 수 있는지 먼저 확인합니다. "이 컬럼이 이렇게 쓰일 거다"라는 가정을 코드로 짜기 전에 검증하는 단계입니다.

- 확인 대상 예시: 사용하려는 컬럼의 결측률(`.isna().sum()`), 값의 분포(`.value_counts()`), 특정 이벤트(예: `Tactical Shift`, `Substitution`)의 발생 빈도, 경기마다 데이터 구조가 달라지는지 등.
- 반드시 **분석 대상으로 실제로 쓸 경기/대회**로 확인하세요. 다른 경기·다른 대회에서 확인된 내용이라도 그대로 일반화하지 말고, 새 주제의 데이터 범위에서 다시 검증합니다(예: `.claude/rules/statsbomb-data-notes.md`의 `position` 컬럼 노트처럼 "이전에 한 경기로 확인했다"는 기록이 있어도, 다른 경기/대회에 적용할 땐 재확인).
- 확인 결과는 기록합니다:
  - 이번 주제에만 해당하는 내용이면 `PLAN.md`의 "데이터 범위"나 "방법론 요약"에 적습니다.
  - 다른 주제에서도 재사용할 만한 일반적인 StatsBomb 데이터 특성이면 [`statsbomb-data-notes.md`](./statsbomb-data-notes.md)에 추가/갱신합니다.
- 검증 결과 방법론을 바꿔야 한다면(예: 표본이 너무 작아 다른 집계 방식이 필요하다면) `PLAN.md` 작성 전에 방법론을 먼저 수정하세요.

### 실행 분담: 메인 세션(판단) + `data-review-run`(실행)

이 단계는 "무엇을 확인할지 정하기 / 스크립트로 옮겨 실행하기 / 결과가 무슨 뜻인지 판단하기"로 나뉩니다. 가운데(전사·실행)만 Haiku 서브에이전트 `data-review-run`에 위임하고, 앞뒤(판단)는 메인 세션이 합니다.

1. **체크리스트 스펙 작성 (메인 세션)** - 방법론이 어떤 가정에 기대는지 짚어, 확인할 항목을 **구체적으로** 못 박습니다. 항목마다:
   - `df 필터` (예: `team == "Spain"` 이고 `type == "Pass"`)
   - `컬럼` 또는 `이벤트 종류`
   - `연산` (`isna().sum()` + `len()` / `value_counts()` 상위 N / `[x,y]` 형태 아닌 값 개수 / `possession`별 성공 패스 수의 평균·중앙값·최소·최대 등)
   - `경기별` 인지 `전체 합산` 인지
   - `자동 플래그 임계값` (예: "결측률 > 1%", "체인 표본 중앙값 < 3")
   - 함께 넘길 것: 대회/시즌/팀 식별자 또는 `match_id` 목록, 템플릿으로 쓸 기존 `scripts/review_*.py` 경로, 스크립트 독스트링에 넣을 "무엇을·왜 검토하는지" 문구
   - 스펙이 구체적일수록 스크립트 작성이 창의성 없는 전사가 되어 Haiku가 안전하게 처리합니다. 애매하게 넘기면 안 됩니다.
2. **전사·실행 (`data-review-run`, Haiku)** - 체크리스트와 템플릿을 받아 `scripts/review_<주제>_data.py`를 작성하고 실행해, 경기별 표 + 전체 합산 + 자동 플래그된 셀을 돌려줍니다. 해석하지 않고, 문서를 건드리지 않습니다. 스펙이 모호하면 추측하지 않고 되던집니다.
3. **검산 + 해석 (메인 세션)** - 돌아온 표를 해석 전에 눈대중으로 검산합니다(예상 범위와 비교 - Haiku가 필터를 잘못 걸었으면 여기서 걸림). 그다음 판단합니다: 표본이 방법론에 충분한가 / 방법론을 착수 전에 수정해야 하는가 / 경기별로 다르게 처리할 부분이 있는가.
4. **기록 (메인 세션)** - 위 "확인 결과는 기록합니다" 규칙대로 `PLAN.md` 또는 `statsbomb-data-notes.md`에 반영합니다.

간단한 확인(컬럼 1~2개 결측률만)이면 메인 세션이 직접 해도 됩니다. 위임은 확인 항목이 여러 개거나 경기 수가 많아 스크립트 이터레이션·`value_counts` 덤프가 길어질 때 이득이 큽니다.

## 3단계 - 분석 주제 폴더 및 파일 구성

`구체화` 상태의 아이디어에 실제로 착수할 때는 프로젝트 루트에 주제별 전용 폴더를 새로 만듭니다(예: `spain_euro2024/`). 이 폴더가 해당 주제의 노트북·스크립트·산출물을 모두 담는 단위가 됩니다.

- 폴더 이름은 팀/주제 + 대회·시즌처럼 짧고 식별 가능하게 짓습니다(예: `spain_euro2024`, `messi_barcelona_career`).
- 폴더 안에 `PLAN.md`(분석 기획 문서)를 먼저 작성합니다. 배경, 분석 질문, 데이터 범위, 방법론 요약(2단계에서 확인한 데이터 검토 결과 반영), 예상 산출물, 진행 상황 체크리스트, 한계를 담습니다. `spain_euro2024/PLAN.md`를 템플릿으로 참고하세요.
- 노트북/스크립트는 폴더 최상위에 둡니다. 단, 한 주제 안에 방법론이 여러 갈래로 나뉘면(예: "패스 네트워크"와 "구역 기반 전진 경로") 방법론별로 하위 폴더를 만들어 그 안에 노트북·`processed/`·결과 문서(`RESULTS.md`)를 두는 것도 허용합니다 - `spain_euro2024/pass_network/`가 그 예시입니다. 이 경우 최상위 `PLAN.md`는 전체 기획을, 하위 폴더의 `RESULTS.md`는 그 방법론의 종합 결과를 담당합니다.
- `ideas/backlog.md`의 해당 항목 상태를 `진행중`으로 바꾸고, 새로 만든 `PLAN.md`로 링크를 겁니다. 착수 시점의 폴더 구조 결정은 필요하다면 `DECISIONS.md`에도 기록하세요.

## 4단계 - 해당 분석 폴더 안에서 산출물 관리

착수 이후의 모든 산출물(이미지, 표, 중간 결과 문서)은 해당 주제 폴더 하위 `processed/`에 저장합니다. `data/processed/`처럼 프로젝트 공용 폴더에 흩어 놓지 않습니다.

- 노트북에서 저장 경로를 잡을 때는 프로젝트 루트가 아니라 해당 주제(또는 방법론 하위) 폴더를 기준으로 상대 경로를 구성하세요(`spain_euro2024/pass_network/04_spain_euro2024_buildup.ipynb`의 `output_dir` 셀 참고).
- 분석이 진행되며 얻은 관찰/결론은 `PLAN.md`의 진행 상황 체크리스트를 갱신하거나, 필요하면 `processed/` 안에 별도 요약 문서를 추가해 기록합니다.
- 분석이 마무리되면 `ideas/backlog.md`의 상태를 `완료`로 갱신하세요.

이 워크플로우는 `ideas/backlog.md`에서 출발하는 주제별 분석에 적용됩니다. `notebooks/01~03`과 `scripts/example_analysis.py`는 프로젝트 최초 셋업 시 만들어진 스타터/예제 자료이므로 이 흐름과 무관하게 그대로 둡니다.

## 서브에이전트 분담 (Claude Code)

이 워크플로우의 일부 단계는 입력·출력이 깔끔하게 격리되어 서브에이전트에 위임할 수 있습니다. Claude Code 전용 기능이며(`.claude/agents/*.md`에 정의), Gemini / Antigravity CLI에서는 해당 작업을 세션에서 직접 수행합니다. 위임의 주된 이득은 병렬화가 아니라 **컨텍스트 격리**입니다(`value_counts` 덤프, grep 출력 같은 노이즈를 메인 스레드에서 치움).

- **`data-review-run`** (Haiku) - 2단계(데이터 검토)의 **실행 부분만** 전담. 메인 세션이 만든 구체적 체크리스트 스펙 + 템플릿 스크립트를 받아 `scripts/review_<주제>_data.py`를 전사·실행하고 경기별 표 + 자동 플래그를 돌려줍니다. "무엇을 확인할지" 정하기와 "결과 해석"은 메인 세션이 합니다 (위 "2단계 - 데이터 검토 / 실행 분담" 참고).
- **`analysis-verifier`** (Sonnet) - 주제 완료 처리 전 또는 큰 문서 갱신 후의 검증 스윕. 먼저 `scripts/check_docs.py`(결정론적: 엠대시/엔대시, 이미지 상대경로, `CLAUDE.md` ↔ `GEMINI.md` 공통 섹션 diff)를 돌린 뒤, 그 위에 판단이 필요한 점검(문서 간 수치 모순, 진행 상태 최신성, blog ↔ 분석 일치)을 얹어 불일치 목록을 돌려줍니다. 읽기 전용 - 고치지 않고 보고만 합니다.
- **`blog-draft`** (Sonnet) - 완료된 주제의 `RESULTS.md`들을 종합해 `blog/<주제>/BLOG_POST.md`(마크다운 원고)를 씁니다. 데이터 저널리즘 톤, 하이픈만. 큐레이션이 필요한 부분(스탯 스트립 수치, 표 강조 행)은 원고에 마커로 지정해 `blog-html`이 창작 판단 없이 변환하게 합니다. 원고까지만 - 제목·프레이밍·발행은 메인 세션이 사용자와 정합니다.
- **`blog-html`** (Haiku) - 확정·윤문된 `BLOG_POST.md`를 `BLOG_POST.html`로 변환. 본문 텍스트는 한 글자도 안 바꾸고, `blog/spain_euro2024/BLOG_POST.html`의 인라인 스타일 템플릿(콜아웃/스탯 스트립/표/figure/한계 박스/푸터)을 매핑 규칙대로 적용하는 포맷 변환만 합니다.

모델: `data-review-run`·`blog-html`은 전사·변환만 하므로 `haiku`로 고정했습니다. `analysis-verifier`(수치 대조 정확도)와 `blog-draft`(글 품질)는 기본 모델(Sonnet)을 상속합니다. 완전 기계적인 검사(엠대시·이미지 링크·문서 diff)는 에이전트가 아니라 결정론적 스크립트 `scripts/check_docs.py`로 뺐습니다 - LLM보다 정확하고 커밋 전 훅 등으로 재사용할 수 있습니다.

**메인 세션이 유지하는 단계** (위임하지 않음): 1단계 아이디어 논의(사용자와의 왕복 대화라 위임 불가), `PLAN.md` 방법론 확정, 분석 실행 + 함수 이터레이션(3~5단계, 산출물을 보며 고치는 반복이 잦음), 산출물 리뷰, `DECISIONS.md`·`PLAN.md`·`backlog.md` 등 문서 갱신. 전 단계를 서브에이전트로 오케스트레이션하는 방식은 cold-start 비용과 맥락 손실 때문에 채택하지 않았습니다(`DECISIONS.md` 2026-08-31 항목 참고).

## 블로그 발행 전 검토 (메인 세션)

`blog-draft`가 `BLOG_POST.md` 원고를 만들면 발행 전 다음 순서를 거칩니다.

1. **사실 대조** - 원고의 수치·결론이 `RESULTS.md`와 일치하는지 확인합니다(`analysis-verifier`를 돌리거나 직접 대조).
2. **제목·프레이밍 확정** - 제목 후보와 글의 초점(무엇을 강조하고 무엇을 뺄지)을 사용자와 정합니다. `blog-draft`가 넣어둔 마커(KICKER / STAT-STRIP 수치 / 표 강조 행)도 이때 함께 검토합니다.
3. **AI 티 윤문** - `humanize-korean` 스킬(`/humanize-korean`)로 확정된 `BLOG_POST.md`를 윤문해, 번역투·영어 인용 과다·기계적 병렬·관용구 남발·불릿/이모지 과다 등 AI 티 패턴을 제거합니다. 이 스킬은 내용·사실·수치·인용을 바꾸지 않고 문체·리듬·표현만 손보며 파이프라인에 content-fidelity 감사가 포함되므로, 수치가 핵심인 데이터 저널리즘 글에도 안전합니다. 윤문 전후로 수치·고유명사가 그대로인지 한 번 더 대조합니다. (윤문 스킬은 자체적으로 서브에이전트를 띄우므로 `blog-draft` 안이 아니라 메인 세션에서 돌립니다.)
4. **HTML 변환** - 윤문이 끝난 `BLOG_POST.md`를 `blog-html`(Haiku)에 넘겨 `BLOG_POST.html`을 생성합니다. 본문은 그대로 두고 인라인 스타일 템플릿만 적용합니다. 변환 후 `blog-html`이 `scripts/check_docs.py`를 돌려 엠대시·이미지 링크를 확인하고, MD와 HTML의 본문 텍스트가 일치하는지 자기 확인 결과를 보고합니다.
5. **발행** - 티스토리 에디터에 본문 + 이미지를 직접 주입하는 방식으로 발행합니다(`DECISIONS.md` 2026-08-31 "티스토리에 직접 발행" 항목).

## 기능 개발/테스트 샌드박스 (`notebooks/`, `scripts/`, `data/`)

`notebooks/`, `scripts/`, `data/`는 특정 주제 폴더에 속하지 않는 공용 샌드박스입니다. 재사용 가능한 함수를 만들고 버전 관리(`src/`로 승격 후 커밋)하거나, 주제 분석 중 필요해진 새 기능을 주제 폴더에 넣기 전에 실험/테스트하는 용도로 씁니다.

- 주제 분석(2~4단계) 도중 `src/`에 넣을 만한 새 함수(예: 새로운 시각화 유형, 데이터 로더 헬퍼)가 필요해지면, 주제 폴더 안에서 바로 만들지 말고 먼저 `notebooks/`(대화형 프로토타입) 또는 `scripts/`(독립 실행 스크립트)에서 구현·테스트하세요. 여러 주제에서 재사용할 코드를 특정 주제 폴더에 묶어두면 나중에 다른 분석에서 찾기 어렵습니다.
- 테스트 과정에서 필요한 중간 데이터나 예제 출력은 `data/`에 둡니다. 주제별 정식 산출물이 아니라 검증 과정의 부산물이라는 점에서 주제 폴더의 `processed/`와 구분됩니다.
- 함수가 검증되면 `src/data_loader.py` 또는 `src/visualizer.py`로 옮겨 정식 커밋합니다 - 이 시점부터 다른 주제 폴더에서도 재사용 가능한 정식 함수가 됩니다. 프로토타입이었던 노트북/스크립트는 지우지 말고 남겨, 그 함수가 어떤 실험을 거쳐 만들어졌는지 추적할 수 있게 하세요.
- 새 프로토타입 파일은 무엇을 테스트하는지 알 수 있는 이름으로 만드세요(예: `notebooks/test_zone_heatmap.ipynb`). 기존 스타터 노트북(`01`~`03`)·`scripts/example_analysis.py`와 섞이지 않도록 구분되는 이름을 씁니다.
